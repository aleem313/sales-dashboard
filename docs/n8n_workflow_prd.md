## 1. Executive summary

The "multiple webhooks" workflow is the **production ingestion pipeline** for Upwork lead automation. It receives jobs scraped by Vollna (one webhook per agent profile), uses an LLM to draft an Upwork proposal, and writes the result into both the Task Board and the analytics Dashboard, on **two parallel deployments** (Vercel + Contabo) so neither environment can become a single point of failure.

A single Vollna POST to a per-agent webhook ends in:
1. A new task on the Task Board (Vercel + Contabo, both via `POST /api/v1/webhooks/tasks`),
2. A new job event on the Dashboard (Vercel + Contabo, both via `POST /api/webhook/n8n`),
3. (legacy) a ClickUp task — kept wired for historical compatibility but ClickUp itself is no longer the source of truth.

The proposal generated by Claude is the work product agents copy and submit on Upwork.

## 2. Goals & non-goals

### 2.1 Goals
- **Per-agent isolation.** Each of 8 agent profiles has its own dedicated webhook URL; Vollna can fail or pause one agent without affecting others.
- **Single source of truth for proposals.** Claude generates one proposal per qualifying job; we never produce duplicates.
- **Dual-environment ingestion.** Every job is delivered to both the Vercel and Contabo deployments in parallel, so a deploy or DB outage on one does not lose leads.
- **Resilient fan-out.** A failure of any downstream sink (ClickUp API, Board API, Dashboard webhook) must NOT block the others.
- **Operational observability.** Every event lands in n8n's execution log with the agent, profile, outcome, and reason fields populated.

### 2.2 Non-goals
- **Status tracking.** Job status (Won, Lost, In Chat, etc.) is owned by the Task Board (column moves) — not by this workflow.
- **De-duplication of jobs across the same workflow run.** Vollna is responsible for not re-posting the same job. The workflow has lightweight per-`job.id` static-data tracking but does not enforce uniqueness.
- **Active-hours filtering.** A `Check Active Hours` node exists but is currently disconnected; weekend/off-hours filtering is **not** active. See §11.
- **Automatic retries from this workflow.** The 4 sinks rely on `neverError: true` rather than retry. See §10.4.

### 5.2 Respond-to-webhook nodes (8)

**Type:** `n8n-nodes-base.respondToWebhook` v1.1
**Purpose:** Close the HTTP connection back to Vollna immediately so Vollna does not wait for the AI pipeline to finish (which can take 5–60 seconds).
**Output:** Each Respond-X feeds the matching `Merge All Webhooks` input index — see §5.3.

### 5.3 Merge All Webhooks

**Type:** `n8n-nodes-base.merge` v3.2
**Parameters:** `numberInputs: 8`
**Input wiring (CRITICAL — restored 2026-04-29):**

| Input index | Source |
|---|---|
| 0 | Respond - Sana |
| 1 | Respond - Laiba |
| 2 | Respond - Khansa |
| 3 | Respond - Saim |
| 4 | Respond - Shayan |
| 5 | Respond - Craig |
| 6 | Respond - Rebekah |
| 7 | Respond - Nawal |

**Why v3.2 specifically:** v3.2 emits downstream when ANY input has data and gracefully ignores empty inputs. v3 emits downstream on every input fire — with 8 inputs, that triggers the AI pipeline 8x for one event, which historically caused OOM crashes on the n8n cloud instance. **Do not downgrade to v3.**

**Why unique input indices matter:** Multiple agents firing concurrently must hit different inputs so n8n's per-execution context isolates them. Sharing an input causes per-agent telemetry blending and (under burst load) item ordering anomalies in downstream nodes.

**Output:** Single edge → `Process Job`.

### 5.4 Process Job

**Type:** `n8n-nodes-base.code` v2 (JS sandbox)
**Purpose:** Parse the inbound webhook, identify the agent profile, normalize the job payload, and emit a `_result` token for `Route Job`.

**Logic:**
1. **Fetch profile mapping** from `/api/profiles/mapping`. Tries Contabo first (`http://157.173.110.62/api/profiles/mapping`), falls back to Vercel (`https://sales-dashboard-snowy-beta.vercel.app/api/profiles/mapping`). Uses `this.helpers.httpRequest()` (n8n-sandboxed `fetch` is unavailable). Empty/error responses on both → emits `_result: 'rejected'`.
2. **Build `PATH_TO_PROFILE`** dynamically from the mapping: `{<lowercase>-profile-webhook → ProfileName}`. This is what makes routing zero-config when a new profile is added — no hard-coded list.
3. **Resolve agent profile** for the inbound event: try matching `headers.path` against `PATH_TO_PROFILE`; if no match (UUID-style webhook), fall back to `body.filter_name || body.filterName || body.filter?.name || body.filter_tag || body.filter`.
4. **Iterate `body.projects`** (Vollna can batch jobs). For each project:
   - Decode the URL (Vollna double-URL-encodes), extract `~<jobId>` from the path, fall back to `p.id || p.job_id || p.uid`.
   - Build the canonical `job` shape (id, title, description, url, budget/budgetType, skills, duration, postedDate, client country/rating/spent/hires/paymentVerified, applicants).
   - If profile name resolves: emit `_result: 'proceed'` with full job + agent metadata.
   - If profile name does NOT resolve in the mapping: emit `_result: 'no_profile'` with the failed `filterName` for triage.
5. If `body.projects` is empty / no valid jobIds: emit `_result: 'rejected'` with reason `"No valid projects in payload"`.

**Emitted `_result` values (today):** `proceed`, `no_profile`, `rejected`. The `Route Job` Switch additionally has rules for `inactive`, `duplicate`, `weekend` — those branches are unreachable until/unless `Process Job` is extended (see §11).

**Output shape (proceed case):**
```json
{
  "_result": "proceed",
  "job": { "id": "...", "title": "...", "description": "...", "url": "...", "budget": "...", "budgetType": "...", "skills": [...], "duration": "...", "postedDate": "...", "clientCountry": "...", "clientRating": "...", "clientSpent": "...", "clientHires": "...", "paymentVerified": false, "applicants": 0 },
  "filterName": "Sana",
  "profile_id": "Sana",
  "profile_name": "Sana",
  "stack": "...",
  "assigned_agent": "...",
  "agent_clickup_id": "...",
  "clickup_list_id": "901815302064",
  "custom_gpt_instructions": ""
}
```

### 5.5 Route Job

**Type:** `n8n-nodes-base.switch` v3
**Switch field:** `$json._result`
**Rules** (in order):

| Output index | `_result` match | Connected to | Reachable today |
|---|---|---|---|
| 0 | `"proceed"` | Build GPT Input | Yes |
| 1 | `"no_profile"` | Format Dashboard Event | Yes |
| 2 | `"inactive"` | Format Dashboard Event | No (dead branch) |
| 3 | `"duplicate"` | Format Dashboard Event | No (dead branch) |
| 4 | `"rejected"` | Format Dashboard Event | Yes |
| 5 | `"weekend"` | (unconnected) | No (dead branch) |

**Fallback:** `options.fallbackOutput: "extra"` — but no edge from the fallback output. Any non-matching `_result` value is silently dropped. This is acceptable today because `Process Job` is the only emitter and it only produces matching values, but a future change to `Process Job` MUST also wire the fallback or extend the rule set.

### 5.6 Build GPT Input

**Type:** `n8n-nodes-base.code` v2
**Purpose:** Construct the user-message string for the AI Agent and pick a hook variant per profile.

**Hook rotation:**
- Per-profile static data (`$getWorkflowStaticData('global').hookRotation[profileId]`) tracks the last hook used.
- Rotation is **A ↔ B only**: `useHook = lastHook === 'A' ? 'B' : 'A'`.
- The system prompt defines three hook types (A: curiosity-led, B: prototype hook, C: psychological question). **Hook C is currently never selected** — see §11 ("Hook C dead").

**Output:** Adds `gptInput` (multi-line string with profile, stack, agent, hook selector, profile-specific instructions, job title, description (first 2000 chars), budget, skills, client context, "Write the proposal now.") to the item. Forwards everything else.

### 5.7 AI Agent - Proposal Writer

**Type:** `@n8n/n8n-nodes-langchain.agent` v3.1
**Prompt type:** `define` — `text` is taken from `{{ $json.gptInput }}`
**System message:** A ~3,500-word Upwork proposal-strategist prompt covering:
- Hard rules (word count 150–230, no emojis/exclamations/hedging, no opening with "Hi/Dear/I am", always reference something specific from the post, end with a call invitation).
- Hook rotation system: agent must print all 3 hook variants (A/B/C) at the top of every response, then write the proposal using the hook the user specified via `USE HOOK:`.
- Project Database (placeholder — not yet populated).
- Section-by-section proposal structure (screening answer, hook, relevance proof, curiosity line, problem understanding, mini-plan, differentiator, strategic question, CTA).

**Output parser:** `Structured Output Parser` returning `{ proposal: string, _proposalOk: boolean }`. `autoFix: true` so malformed outputs are repaired by the LLM.

**LLM:** `Claude Chat Model - Proposal` (Claude Haiku 4.5, temp 0.2, credential `Aleem Anthropic account`).

### 5.8 Merge Proposal with Job Data

**Type:** `n8n-nodes-base.set` v3.4
**Purpose:** The AI Agent only outputs `proposal` and `_proposalOk` — re-attach the original job/profile data via `$('Build GPT Input').item.json` so downstream nodes have the full context.

**Set fields:**
- `proposal` ← AI output
- `_proposalOk` ← AI output
- `job`, `profile_id`, `profile_name`, `stack`, `assigned_agent`, `agent_clickup_id`, `clickup_list_id`, `filterName` ← from Build GPT Input

`includeOtherFields: true` so the rest of the item is preserved.

### 5.9 Proposal OK?

**Type:** `n8n-nodes-base.if` v2
**Condition:** `$json._proposalOk === true`
- **True branch** → `Format ClickUp Task`
- **False branch** → `Extract Error`

### 5.10 Extract Error

**Type:** `n8n-nodes-base.code` v2
**Purpose:** Build a minimal `gpt_error` payload from a failed proposal item, mark the job as `gpt_failed` in static data (so retry logic — if added later — can detect it), and forward to `Format Dashboard Event`.

**Output:**
```json
{ "job_id": "...", "job_url": "...", "job_title": "...", "profile_id": "...", "profile_name": "...", "assigned_agent": "...", "error_detail": "..." }
```

### 5.11 Format ClickUp Task

**Type:** `n8n-nodes-base.code` v2
**Purpose:** Build the rich-emoji task body shared by all four downstream sinks (ClickUp, both Board APIs, and Format Dashboard Event).

**Outputs added to the item:**
- `taskName` — `[{profile_name}] {jobTitle}`, truncated to 100 chars
- `taskDescription` — multi-section emoji-formatted Markdown:
  - Proposal block (copy-and-send-as-is)
  - Job Snapshot (link, budget, skills, posted)
  - Client Intel (location, rating, total spent, past hires)
  - Routing Info (agent, profile, stack, job ID, generated timestamp UTC)
- `taskBody` — ClickUp-shaped object: `{ name, markdown_description, assignees: [Number(agent_clickup_id)], priority: 2, due_date: now+24h, due_date_time: true, tags: [profile_name, 'vollna-auto'] }`

**Side effect:** Marks `staticData.seenJobs[job.id] = { status: 'success', timestamp: Date.now() }`.

### 5.13 Format Dashboard Event

**Type:** `n8n-nodes-base.code` v2
**Purpose:** Normalize an item from any of the upstream paths (success, no_profile, rejected, gpt_error) into a single dashboard event shape.

**Outcome derivation logic:**
```js
let outcome = item._result || 'unknown';
if (clickupTaskId)                    outcome = 'proposal_created';
else if (item.taskName && item.proposal) outcome = 'proposal_created';
else if (item.error_detail)            outcome = 'gpt_error';
```

So the dashboard receives one of: `proposal_created`, `gpt_error`, `no_profile`, `rejected`, `unknown`. (`weekend`, `inactive`, `duplicate` are never produced today.)

**Note on the success path:** `Format Dashboard Event` is also wired DIRECTLY downstream of `Format ClickUp Task` (one of the four fan-outs). On that path, `$('Format ClickUp Task').item.json` is pulled to get the rich pipeline state, and `clickupTaskId/Url` are always `null` because the ClickUp HTTP response has not arrived yet. This is intentional — the dashboard should not block on ClickUp.

### 5.14 Check Active Hours (currently DISCONNECTED)

**Type:** `n8n-nodes-base.code` v2
**Intended behavior:** Drop every event outside Mon–Fri 16:10 → 02:00 Asia/Karachi. Implementation:
- `getDay()` 0 (Sun) or 6 (Sat) → return `[]`.
- Convert PKT current minute-of-day; pass through if `minute >= 16:10` OR `minute < 02:00`.

**Current state:** Zero inbound, zero outbound connections. The active path is `Merge All Webhooks → Process Job` directly. Weekend and off-hours events flow through unchecked.

**To re-enable:** Splice between `Merge All Webhooks` and `Process Job` (1 `removeConnection` + 2 `addConnection` ops via partial update).

```jsonc
{
  "Sana":    { "profile_id": "...", "stack": "...", "assigned_agent": "...", "agent_clickup_id": "...", "clickup_list_id": "..." },
  "Laiba":   { ... },
  // ... one entry per active profile
}
```

`Process Job` fetches this on **every execution** (no n8n-side cache). Contabo is primary, Vercel is fallback. Admin assignment changes from the Settings UI propagate to the next inbound webhook.

**Path resolution priority in `Process Job`:**
1. `headers.path` ⊇ `<lowercase-name>-profile-webhook` → match (works for Rebekah/Nawal).
2. Fall back to `body.filter_name || body.filterName || body.filter?.name || body.filter_tag || body.filter` → works for the 6 UUID-style webhooks because Vollna sends `filter_name` in the body.

**Adding a new agent profile** is documented in CLAUDE.md ("Adding a New Profile/Webhook Node to n8n"). At the workflow level it requires: addNode (Webhook + Respond), addConnection (Webhook → Respond, Respond → Merge with `targetIndex = N`), updateNode (`Merge All Webhooks.parameters.numberInputs += 1`).

### 8.1 Three hook types

| Hook | Style | Formula | Max length |

### 8.2 Rotation today

`Build GPT Input` only rotates between **A** and **B** per profile. Hook **C** is defined in the system prompt (the agent must print all three at the top of every response) but is never selected by `USE HOOK:`. The user-visible proposal always uses A or B in Section 1.

### 8.3 Output formatting requirement

The agent prints `--- Hook A ---`, `--- Hook B ---`, `--- Hook C ---` blocks at the top, then the full proposal below. Agents copy the proposal section only into Upwork.

## 10. Operational requirements

### 10.1 Latency budget

| Phase | Typical | Notes |
|---|---|---|
| Webhook → Respond | <100ms | Vollna's connection closes here |
| Process Job (incl. profile fetch) | 100–500ms | Network-bound by `/api/profiles/mapping` |
| AI Agent (Claude Haiku 4.5, temp 0.2) | 5–20s | Claude p99 is ~30s; Haiku is the fastest tier |
| Format + 4 sinks (parallel) | 200–800ms | Bound by slowest sink (usually ClickUp or Vercel) |
| **End-to-end success path** | **6–22s** | |

### 10.2 Concurrency

n8n cloud runs each webhook trigger in its own execution. The Merge node v3.2 with 8 unique inputs ensures concurrent agent jobs are isolated.

### 10.3 Active hours

**Currently disabled.** The workflow processes jobs 24/7 including weekends. Vollna is the gating mechanism: agents pause/resume their own Vollna feeds outside working hours.

To re-enable: see §11.

### 10.4 Retry policy & failure modes

| Failure | Behavior |
|---|---|
| Vollna POST hits an n8n save-time blip (~1–2s during a workflow update) | Webhook returns 404; **lost event** (Vollna does not retry) |
| `Process Job` fails to fetch profile mapping (both Contabo + Vercel down) | Emits `_result: 'rejected'` → goes to Format Dashboard Event → both dashboards record a `rejected` outcome |
| Claude API error / malformed output | Output parser autoFix attempts repair; if `_proposalOk: false` → Extract Error path → `gpt_error` outcome |
| ClickUp 4xx/5xx | `retryOnFail: true, maxTries: 3, waitBetweenTries: 2000`; if all fail, `onError: continueRegularOutput` continues the pipeline |
| Vercel Board API down | `neverError: true` swallows the error; **no retry**, no failover |
| Contabo Board API down | Same — swallowed, no retry |
| Vercel Dashboard webhook down | Same — swallowed, no retry |
| Contabo Dashboard webhook down | Same — swallowed, no retry |

**Asymmetry:** Only the legacy ClickUp sink retries. The four active sinks rely on `neverError`. A transient 503 on a Dashboard or Board API loses that single event with no record. See §12.

### 10.5 Rollback procedure

The committed snapshot at `docs/multiple webhooks (working flow).json` is the source-of-truth pre-2026-04-29 state. Plus n8n's internal versioning (`mcp__n8n-mcp__n8n_workflow_versions`).

**To rollback the Merge index fix:**

## 14. Glossary

| Term | Meaning |
|---|---|
| **Vollna** | External Upwork-feed scraper that posts matched jobs to per-agent webhooks |
| **Profile** | A named Vollna filter / Upwork persona owned by one agent (e.g. "Sana", "Nawal") |
| **Filter name** | The string Vollna sends to identify which profile the job is for; the workflow uses it to look up the agent |
| **Hook** | The opening 1–2 sentences of the proposal designed to maximize open/response rate |
| **Outcome** | The terminal label of a workflow execution from the dashboard's perspective: `proposal_created`, `gpt_error`, `no_profile`, `rejected`, `unknown` |
| **Sink** | An outbound HTTP destination (ClickUp API, Board API, Dashboard webhook) |
| **Board API** | `POST /api/v1/webhooks/tasks` — creates a Task Board task |
| **Dashboard webhook** | `POST /api/webhook/n8n` — creates a `jobs` row, auto-assigns an agent, optionally creates a board task with `_source: n8n` |
| **PKT** | Asia/Karachi timezone (UTC+5) |
